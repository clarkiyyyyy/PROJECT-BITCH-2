01

Module

Execution Fundamentals

Threads, processes, and the boundary between them.

Definition panel

Thread

The smallest sequence of instructions that a scheduler can execute independently. Threads of one process share the same memory, open files and resources.

Process

An independent running program with its own address space. Processes are isolated from each other and communicate through explicit mechanisms.

Program

A passive file stored on disk. It becomes a process only when it is loaded and the operating system allocates resources for it.

Comparison rows · threads against processes

AttributeThreadProcess
MemoryShares the process address spaceOwn private address space
Creation costLightweight, mostly registers and a stackHeavy, a full address space must be built
CommunicationDirect through shared memoryRequires IPC: pipes, sockets, messages
Context switchGenerally fasterGenerally slower
IsolationLow — a bad write can corrupt the processStrong — one process cannot touch another
FailureA crash usually takes the whole process downUsually contained to that process

Inline diagram · one process, three threads

Numbered explanation · from file to running threads

  1. 1

    The program file is read from disk and its instructions are mapped into memory.

  2. 2

    The operating system creates a process, allocating an address space, a heap and file handles.

  3. 3

    The main thread starts executing instructions from the entry point of that process.

  4. 4

    Additional threads are created. Each receives its own stack and register set but shares the heap.

  5. 5

    The scheduler gives CPU time to ready threads, interleaving them on one core or running them together on several.

Expandable note · why threads are described as lightweight

Creating a thread does not require building a new address space. The kernel or runtime copies a small register set and allocates a stack, so thread creation costs a fraction of process creation. The trade-off is that the cheap sharing which makes threads fast also removes the isolation that protects processes from each other.

Module

Concurrent Execution

Concurrency, parallelism, context switching and scheduling.

Comparison rows · concurrency against parallelism

Concurrency

  • Several tasks make progress during overlapping periods
  • Works on a single core by switching between tasks
  • Measured by responsiveness, not raw speed

Parallelism

  • Two instructions truly execute at the same instant
  • Requires more than one core or processor
  • Measured by throughput on CPU-bound work

Every parallel system is concurrent, but a concurrent system is not necessarily parallel. Concurrency is a way of structuring work; parallelism is a hardware capability.

Numbered explanation · inside one context switch

  1. 1

    The running thread is interrupted by a timer, an I/O event or a blocking call.

  2. 2

    Its registers, program counter and stack pointer are saved into its control block.

  3. 3

    The scheduler selects the next ready thread from the run queue.

  4. 4

    The saved state of that thread is restored and execution continues exactly where it stopped.

  5. 5

    The whole operation costs time, so very small time slices waste CPU on switching alone.

Mini table · switch cost

Switch typeWhat must be savedRelative cost
Thread → threadRegisters and stack pointer, same address spaceLower
Process → processRegisters plus a full address space and cache stateHigher
Expandable note · scheduling decides everything you observe in the lab

A scheduler chooses which ready task runs next using a policy such as first-come first-served or round robin. The same set of tasks can therefore finish in a different order, and a task that finishes last is not necessarily the longest one. The scheduling playground in the Visual Lab lets you compare both policies on the same input.

03

Module

Shared Resources

Synchronization, locks, semaphores and critical sections.

Definition panel · what synchronization is for

Shared mutable state

Any value that more than one thread can both read and change. Counters, caches, file positions and connection pools all qualify.

Critical section

The stretch of code that reads and writes that value. Only one thread may be inside it at a time, otherwise updates overwrite one another.

Mini table · synchronization tools

ToolWhat it doesTypical use
Lock / mutexGrants exclusive access to one thread at a timeProtecting a counter or a file position
SemaphoreLimits how many threads may enter simultaneouslyA pool of N database connections
Condition variableBlocks a thread until a condition becomes trueWaiting for a queue to become non-empty
Event / signalWakes every thread listening for a notificationAnnouncing that a shutdown was requested

Diagram · two workers, one gate, one resource

While one worker holds the lock, the second waits outside the gate. Reads and writes therefore happen one after another instead of interleaving.

Numbered explanation · rules for a critical section

  1. 1

    Identify every value that two threads can both read and write.

  2. 2

    Acquire the lock before reading, keep the section as small as possible, then release it.

  3. 3

    Always acquire multiple locks in the same global order to avoid circular waiting.

  4. 4

    Never block or perform slow I/O while holding a lock — other threads queue behind you.

Expandable note · protection is not free

Every lock adds bookkeeping and can force threads to wait. Synchronize only what needs protecting, prefer one clear lock over several overlapping ones, and measure before adding finer-grained locking. An unprotected fast program that returns wrong answers is still slower than a correct one.

Concurrency Problems

Race conditions, deadlocks, and how each one is prevented.

Numbered explanation · a lost update

Shared counter = 0Two workers · one increment each
  1. 1

    Worker A reads the current value, 0.

  2. 2

    Worker B reads the value as well — still 0, because A has not written yet.

  3. 3

    Worker A writes 0 + 1 = 1.

  4. 4

    Worker B writes 0 + 1 = 1, overwriting A's result.

Expected2
Actual1

The failure is silent. No exception is raised; the program simply returns a wrong number. Run it again and the timing may produce the correct answer, which is exactly what makes race conditions hard to reproduce.

Numbered explanation · four necessary conditions

  1. 1

    Mutual exclusion. At least one resource can be held by only one worker at a time.

  2. 2

    Hold and wait. A worker holding one resource keeps asking for another.

  3. 3

    No preemption. Resources cannot be taken away; they must be released voluntarily.

  4. 4

    Circular wait. A closed chain of workers each waits for the next.

A deadlock needs all four at once. Breaking any single condition — usually by forcing a consistent request order — removes the possibility.

Comparison rows · race condition against deadlock

SignalRace conditionDeadlock
ThreadsKeep running to the endStop making any progress
CauseUnsynchronized access to shared dataCircular wait on held resources
SymptomWrong or unstable resultsProgram appears frozen
FixLock the critical sectionRequest resources in one global order
Expandable note · starvation is the third failure mode

Starvation is the quieter sibling of both problems. Nothing is corrupted and nothing is stuck — a thread is simply never scheduled or never wins the lock, so its work never finishes. Fair locks and reasonable priorities are the usual defences.

05

Module

Practical Threading

Python threading, the GIL, and choosing the right tool.

Code workbench · five workers in Python

worker_threads.py Python 3 
import threading
import time
import random


def worker(worker_id):
    delay = random.randint(1, 3)
    time.sleep(delay)
    print(f"Worker {worker_id} finished")


workers = []

for i in range(5):
    worker_thread = threading.Thread(
        target=worker,
        args=(i + 1,)
    )
    workers.append(worker_thread)
    worker_thread.start()

for worker_thread in workers:
    worker_thread.join()

print("All workers completed")

Explanation

Thread object
threading.Thread(...) describes the work: the function to run and the arguments to pass. Creating it does not run anything yet.
start()
Requests a new OS thread and schedules worker. Calling it twice on one object raises an error.
sleep()
Releases the thread for a period. In real code this stands in for network waits or disk reads — the exact work where threads pay off.
join()
Blocks the caller until that worker finishes, which is how the final message is guaranteed to print last.

Execution notes

  1. 1

    Five thread objects are created inside the loop.

  2. 2

    Each start() returns immediately, so the loop finishes long before the workers do.

  3. 3

    The workers now overlap: total runtime approaches the longest single delay, not the sum of all five.

  4. 4

    join() is called on every worker before the last print statement runs.

Mini table · the GIL and workload choice

WorkloadWhere time goesBetter fit in CPython
I/O-boundWaiting on network, disk or databasesThreads — the GIL is released during waits
CPU-boundContinuous arithmetic and logicMultiprocessing — one interpreter per core
MixedReading data, then computing on itThreads for the wait, processes for the compute

The global interpreter lock allows only one thread to execute Python bytecode at a time. Threads still overlap their waiting, but they will not speed up pure computation on their own.

Checklist · habits for predictable concurrent code

  • Keep critical sections small and free of I/O.
  • Protect every shared mutable value, even counters.
  • Acquire multiple locks in one consistent global order.
  • Join threads whenever the program must wait for them.
  • Test the same code under different timing conditions.
  • Prefer one clear synchronization design over several clever ones.

    About CONCURRA

    An original learning workspace for operating-system concurrency, built as a single static page with plain HTML, CSS and JavaScript.

    What this is

    CONCURRA organises the same subject matter you would study in an operating systems course — threads, processes, concurrency, shared resources, race conditions, deadlocks, scheduling and Python threading — inside an application-style workspace instead of a long landing page.

    Every simulation runs on browser timers. Nothing here creates real operating-system threads, and no results should be read as performance benchmarks. The purpose is to make the timing relationships visible, one experiment at a time.

    How your data is handled

    • No account, no server, no database, no network requests for your data.
    • Progress, scores and experiment history are stored in this browser with localStorage.
    • Clearing site data for this page resets the workspace completely.
